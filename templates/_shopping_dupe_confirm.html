{# Phase 6D: shopping duplicate-add confirmation card. Rendered by `shopping_add` when a POST /shopping name matches an existing shopping item in the household (case-insensitive, trimmed). The pending values live in this card's hidden inputs; the three buttons resolve the ambiguity: - Update existing (+2 gallon) → POST /shopping/merge/. Merges quantities + notes into the existing row. Card clears via OOB. - Add as separate row → POST /shopping?force_duplicate=1. Skips the dupe check, creates a second row. Card clears via OOB in the same swap that updates the list. - Cancel → Pure client-side. Removes the card from the DOM. The user's typed values remain in the add form (server sends HX-Detour so shopping.html's after-request handler suppressed the auto-reset), so they can tweak the name and re-submit without re-typing quantity/unit/notes. Shopping-specific detail vs the pantry twin (_pantry_dupe_confirm.html): we surface the existing row's `checked` state as a subtle badge so the user has full context on which row they're about to merge into. If they see "already crossed off", they know "Add as separate row" will create a fresh un-checked row for the extra qty they need — vs "Update existing" which will bump the checked row's quantity and leave it crossed off. See `_merge_pending_into_shopping_item` for why we don't mutate `checked` on merge. Context: existing — the ShoppingItem we matched against (household- scoped). Displayed as reassurance ("here's the row we mean"). pending_form — the validated ShoppingItemForm with the user's pending data. Rendered as hidden inputs so the merge/add-anyway POSTs carry it forward. #}
